## 反 Gank 小地图哨兵（D:/anti-gank）

从零搭了一个 LOL 实时反 gank 工具，最终形态是纯 CV + 官方接口混合，没有用视觉大模型。

### 关键技术决策
- **拒绝用云端视觉 API 做逐帧判断**。实测依据：云端 VLM 单帧 400ms–2.5s、一局 18000 次调用、
  二分类准确率 85–92%；而红色环检测 1.46ms、召回/准确 100%（合成数据）。大模型只适合放策略层。
- **采集用 GDI(mss)**，DXGI 作为可选后端。原因：只需抓 280×280，且机器上有向日葵 Oray IDD +
  MuMu 虚拟显示适配器，dxcam 极易选错 output。
- **身份不靠像素猜**：官方 Live Client Data API (`127.0.0.1:2999/liveclientdata/allgamedata`)
  给敌方 5 人英雄名（不给坐标），小地图给位置，用 Data Dragon 头像模板归一化互相关对上号。
- **地图分区用可验证的几何**：中路 = 主对角线 `nx+ny=1`（两基地恰在这条线两端），
  河道 = 副对角线 `nx=ny`（大龙坑 0.28,0.28 / 小龙坑 0.72,0.72 都在这条线上），
  且河道正好是两基地连线的中垂线 → 天然切出蓝/红半区，再叠加上/下路得到四个野区块。

### 踩到的坑（重要）
1. **模板遮罩半径**：小地图头像是"方形原画裁圆 + 外圈红描边"，描边不携带身份信息。
   遮罩 0.46 时 top-1 只有 66.7%，0.34 时 91.3%。已固化 0.34。
2. **"到中路中心线的垂直距离"不能用来判危险**：中路贯穿全图，敌方基地那头贴着中路的敌人
   垂直距离同样小 → 疯狂误报。改成统一用「到参考点(0.5,0.5)的预计到达时间 TTA」一个指标。
3. **Data Dragon zh_CN 的 name/title 是反的**：`name` 是称号（九尾妖狐），`title` 才是名字（阿狸）。
   已交换成 `epithet`/`name` 字段。
4. **首帧计时陷阱**：OpenCV 首次 detect 19ms（线程池预热），稳态 1.46ms；GDI 首帧 136ms。
   doctor 里已加预热 + 丢前 6 帧，否则会误报 20 倍慢。
5. **BitBlt 在本机 16.5ms，且与区域大小无关**（100²和800²一样）→ 是固定开销，
   裸 ctypes 验证同样是 16.57ms，不是 mss 的锅。怀疑软件合成桌面。GetDIBits 仅 0.09ms。

### 实测数据
- 检测：1.46ms p50（280×280），合成数据召回 100% / 准确 100%
- 身份：单帧 top-1 91.3%（173 英雄 5 选 1）
- 采集：17–18ms（本机环境问题），内存 200–280MB，显存 <1MB
- 语音：198 条 wav（25 短语 + 173 英雄名），SAPI 中文 Huihui，rate=300，共 7MB

## 播报没有英雄名（21:55）

用户反馈报警只报位置、不报英雄名。排查结论：**语音文件没问题（178 个 champ_*.wav 全在，
0.7~0.9s），问题在于报警发生时 `tr.key` 还是 None**。

### 三处根因
1. `Track.add_identity` 要 **3 票**（`min_votes=3`）。1 Hz 下等于 3 秒才认得出，
   但第一次 sight 在 0.5 秒就触发了 → 永远说不名字。
2. 敌人进草/漏帧后轨迹重建，`votes` 跟着清零 → 刚才叫得出名字，转头又变成"敌人"。
3. `_sighting` 里区域状态是**先提交后播报**，如果为了等名字而 return，情报就被吞掉。

### 修法
- `add_identity(key, score)`：单帧相关度 **≥0.86 直接认定**（真机实测正确识别 0.95+），
  否则 **2 票** + 45% 占比。
- `Tracker._inherit`：新轨迹若在 `2×gate` 半径内、且 3 秒内有已命名的旧轨迹 → `adopt()` 继承身份。
- `confirmed()`：**已命名的轨迹不再受"静止=建筑"过滤**（回城/蹲草/补刀不会丢），
  静止兜底只用于身份未知的目标。`static_hold` 4s 保留。
- `threat.identity_grace = 1.8s`：名字没解析出来时，sight/warn/fog 压后最多 1.8 秒；
  **danger 不压**（贴脸等不起）。`_sighting` 里把 `st.zone = committed` 移到等待判断之后。
- 无名兜底：新增短语 `enemy` =「有敌人」（`assets/voice/enemy.wav`），
  seq 变成 ('enemy','zone_xxx')，宁可无名也不漏报。

### 验证
- 新增 `tools/test_name.py` 5/5：已识别直接带名 / 延迟解析不抢跑 / 始终无名仍播报 /

正贴在右边缘红塔旁（下路），旧代码报"红方下路野区"。

## 23:05 修「检测到了但没声音」——pyttsx3 两个致命坑
- 现象：控制台一直在打「播报 敌方XX出现在XX」，耳机一句都没有。日志 `[voice] 已生成语音`
  只打印到第 3、4 条就停（本局 5 个敌人）。
- 根因1：`synth_wav` 里合成完调 `eng.stop()` → 下一次 `pyttsx3.init()` **永久挂起**。
  实测：p2.py(不调 stop) 3/3 正常；p3.py(调 stop) 第 0 句 OK 后卡死，40s 超时。
  修法：只 `del eng` + `gc.collect()`，绝不 stop。连跑 10 句 2.1s 全成。
- 根因2：pyttsx3 **一个进程只认第一个用 SAPI 的线程**。第二线程 init 不报错，只是
  runAndWait 立即返回失败、文件不生成（实测 A 线程 6/6 成功、B 线程 6/6 全 False）。
  真实场景里 `_prebuild_names` 后台线程抢到 TTS，播放线程整场哑着，且被 `except: pass` 吞掉。
  修法：Voice 内加单合成线程 `_syn_worker` + `_syn_q`，`_synth_sync` 投递并等 Event(30s)；
  `line_path` 用 per-path Lock 防重复合成；`_prebuild_names` 改走 `vc.prepare(items)`。
- `_play` 不再静默：异常计入 `vc.play_fail` 并打印前 3 条「播放失败」。
- 新增 `main.py saytest`：合成 3 句逐句播，输出区分「合成失败 / 播了没声 / 播放报错」。
- 新增 `tools/test_voice.py` 5 用例（缓存命中、3 线程并发×4 句、连做 6 次、时长卡控、
  prepare 幂等）。全部通过。
- 并发模拟（prebuild 10 条 + warmup 2 句 + 主线程 2 条播报）：10/10、2/2、play_fail=0，3.9s。
- 回归：test_voice 5/5、test_behaviour 8/8、test_name 7/7、test_zone 28/28、test_real、

### 野区边界收窄（本轮最后一条需求）
